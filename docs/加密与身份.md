# 加密与身份

这份文档记录「传输加密 + 身份核验 + 身份迁移 + 内网服务器可用性」这一整套
改造的设计取舍。代码分布在三处：

| 位置 | 作用 |
|---|---|
| `src/crypto/` | 客户端密码学（无任何第三方依赖） |
| `server/src/identity.mjs` | 服务端身份核验 |
| `server/src/index.mjs` | 握手流程接进 WebSocket |

`src/crypto/` 里四个文件的层次：

```
core.ts       base64 / UTF-8 / 随机数 / AAD 拼接 / base32 —— 没有密码学，只有搬运
keys.ts       身份密钥对（Ed25519 + X25519）、导出导入、指纹、安全码
envelope.ts   内容加密（AES-GCM）、密钥协商（X25519+HKDF）、包会话密钥、签名
session.ts    把上面这些接成「一个会话一把钥匙」的管理器
```

---

## 一、为什么要动这一块

原来的实现有一个**真实的、可被利用的漏洞**：

```
客户端: { op: 'auth', token: 'anonymous' }
服务端: 好，你是 u_admin
```

`src/transport/websocket.ts:178` 当年发的 auth 帧里连 `selfId` 都没有，
服务端（`server/src/index.mjs` 的 auth 分支）于是无条件用 `DEFAULT_SELF_ID`。
也就是说：**每个人连上来都是管理员**，而且谁想当李织烟都行。

这不是「不够安全」，是「没有身份」这个概念。所以这次改造的核心一句话是：

> **身份不是字符串，是一对公钥。**

名字（`u_lizhiyan`）只是贴在那把公钥上的标签。标签可以改，公钥不会变。
服务器记住的是公钥。要证明「我是我」，就得当场用私钥签一段话。

## 二、身份：挑战应答，而不是口令

### 流程

```
客户端 → auth { token, selfId, name, ed: <Ed25519 公钥> }
服务端 → challenge { nonce, serverId, mode: 'register' | 'login' }
客户端 → auth { token, signature }          # 用私钥签 (nonce, serverId, selfId)
服务端 → hello { verified: true, ... }
```

没有配身份密钥的客户端会跳过第二段（服务端记为 `verified: false`），
这条兼容路径保证老客户端不会因为这次改造而连不上。

### 待签的那段文本，以及为什么是这几样

```
baker-auth-v1 \0 nonce \0 serverId \0 selfId
```

四段各自防一件事：

| 段 | 防什么 |
|---|---|
| `baker-auth-v1` | 以后换格式时老客户端明确失败，而不是悄悄用一个错的格式登进去 |
| `nonce` | 一次一签。截获了也没法重放——服务器每次都给新的 |
| `serverId` | **中间人把 A 服务器的挑战转发给你、骗到签名后拿去 B 服务器登录** |
| `selfId` | 拿自己的钥匙去签别人的名字 |

第三行是最容易被忽略、也最危险的一条。少了 `serverId`，攻击者只要能让
你连上一次他的服务器，就能拿你签的东西去登任何一台服务器。

四段之间用 `\0` 分隔，因为 `\0` 不可能出现在 nonce（base64）、serverId 或
selfId 里 —— 否则 `("ab","c")` 和 `("a","bc")` 会拼出同一串字节，签名就有歧义。

**服务端和客户端各有一份独立实现**（`signingMaterial()` / `authMaterial()`），
`tools/crypto-selftest.ts` 会直接 import 服务端那份来逐字节对拍。
这是整条链路上最容易悄悄错的地方：差一个分隔符就永远登不上，
而且报错只会是「验签失败」，看不出是哪边的问题。

### TOFU：第一次见到就钉住

服务器第一次见到某个名字的公钥就存下来，之后**换一把钥匙连同一个名字会被拒**
（`identity_taken`）。这叫 TOFU —— Trust On First Use。

为什么不每次都用客户端报上来的公钥：那样攻击者连上来报自己的公钥，
照样能证明「我持有这把私钥」，核验等于没有。

TOFU 的强度上限是「你第一次连的时候中间没有人」。所以才有下面这个：

### 指纹与安全码：把 TOFU 补成真的

- **指纹**（`AC10-JK8Y-N2RW-M2TV`）：两个公钥一起哈希 —— 这样指纹同时锁住
  「签名身份」和「加密身份」，只锁一个的话另一个可以被偷换而指纹不变。
  用途是**线下核对**：当面或电话里念一遍，确认服务器给的是真货。
- **安全码**（12 组 5 位数字）：双方公钥排序后哈希，所以两个人各自算出来
  必须一模一样。不一样 = 中间有人换过公钥。

两个都用去掉 `I/L/O/U` 的 Crockford base32 —— 因为它们是要**念出来**的。

## 三、传输加密

### 原语全部用浏览器/Node 自带的 WebCrypto

| 用途 | 算法 |
|---|---|
| 签名 / 身份 | Ed25519 |
| 密钥协商 | X25519 + HKDF-SHA256 |
| 内容加密 | AES-256-GCM |
| 指纹 / 安全码 | SHA-256 |

一行 import 都不用加（`tweetnacl` / `libsodium` / `@noble` 全部不需要）。
少一个依赖就少一份供应链风险，而且 AES-GCM 走 CPU 的 AES-NI 指令。

### 信封格式

```json
{ "v": 1, "iv": "<base64>", "ct": "<base64>" }
```

AAD（附加认证数据，不加密但参与完整性校验）绑定四样：

```
sessionId | keyVersion | authorId | seq
```

这样攻击者即使能改服务器，也没法：
- 把一条消息**挪到另一个会话**（sessionId 变了，标签对不上）
- 把消息**冒充成别人发的**（authorId 变了）
- **重放**第 2 条冒充第 1 条（seq 变了）

AES-GCM 的解密失败会抛异常，`open()` 统一返回 `null` —— 调用方只需要判空。

### 密钥包的 AAD 绑的是「会话 + 发件人 + 收件人」

装在 `key` 事件里那一份包起来的会话密钥，自己的 AAD 是：

```
wrap | sessionId | senderId | recipientId
```

三样缺一不可，因为**每一样都堵住一条真实的攻击路径**：

| 少了谁 | 能干什么 |
| --- | --- |
| `recipientId` | 把「给 A 的包」原样转发给 B，B 以为这是发给自己的 |
| `senderId` | 把「A 发的包」说成是自己发的，冒充建钥人 |
| `sessionId` | **把包在会话之间搬运**（见下） |

最后一条不是凑数的，它的方向是**读别人的消息**。同一对 sender/recipient
同时在两个群里时：Mallory 是 S1 和 S2 的成员，她把日志里「爱丽丝为 S1 写给
鲍勃的那份包」原样塞进 S2 的 `key` 事件。鲍勃解出来的是爱丽丝的 **S1** 密钥，
于是他在 S2 里用 S1 的钥匙加密 —— 而 Mallory 手里有 S1 的钥匙，鲍勃在 S2
里说的每一句话她都能读；对爱丽丝则表现为「鲍勃在 S2 的消息全是打不开的气泡」。

所以这个 AAD 里**没有留旧格式的兼容分支**：绑上 `sessionId` 之前发出去的包
一律解不开，这是有意的取舍（留兼容就等于把上面那个洞留着）。代价可恢复 ——
本地取不回自己那把时，`ensureSessionKey` 会走「重建 / 补包」那条路重发一份，
不需要用户做任何事。

### 密钥分发：一次性包，而不是每次协商

1:1 会话里，发起方用一个临时 X25519 密钥算共享秘密，
把会话密钥包成信封挂在会话上：

```json
{ "epk": "<临时公钥>", "iv": "...", "ct": "<包起来的会话密钥>" }
```

接收方用自己的私钥 + 对方的临时公钥解开，得到同一把会话密钥。
**之后每条消息只加密一次**，服务器从来拿不到明文密钥。

（会话密钥分发的**群聊**部分还没接进消息路径，见「已知缺口」。）

## 四、身份迁移：私钥是可导出的

身份 = 两对私钥。它们在 `generateIdentityKeys()` 里是 `extractable: true` 的。

**这是一个刻意的取舍**：私钥导出意味着它的拷贝可能落在磁盘上、剪贴板里、
聊天记录里 —— 攻击面比不可导出的密钥大。换来的是「换台机器还是同一个人」。

私钥永远不出设备，导出的身份包由用户自己保管。
跨服务器迁移时，新服务器用包里的公钥去核对，
而**真正的信任来自「用包里的私钥签一段挑战」** —— 那是登录时走的路。

## 五、已知缺口与已知成本

诚实列一下现在**没做**的：

1. **密钥一旦出岔子就静默降级成明文。**
   拿不到会话密钥时消息照常发出去，只是正文留在外面 —— 这是有意的取舍
   （不阻塞用户），但**没有拦**。界面上现在会显示一条明文提示
   （`PlaintextNotice`），这一点原先是缺的：代码里写着「界面上会有提示」，
   而整个 `src/components` 里没有任何一处提过加密状态。
   要做得更严，应该在明文发送前先问一次用户。
   加密路径本身是通的：1:1 与群聊共用 `src/crypto/session.ts` ——
   建钥人（成员里 id 最小的那个）建钥匙、给每个成员各包一份；
   收到更高版本时会轮换，并把旧版本的钥匙留在 `history` 里以便继续读历史。
2. **服务器仍然能看到 1:1 之外的明文元数据** —— 谁在什么时候跟谁说了话。
   内容加密了，信封（sessionId / authorId / 时间）没有，这是刻意的：
   服务器要路由就必须知道这些。
3. **没有前向保密。** 会话密钥一旦泄露，之前抓到的密文全部可解。
   要做成 Signal 那种双棘轮（每条消息换一次密钥）才能解决。
   取舍理由：双棘轮要求消息严格有序，而这是个多设备、可能乱序的聊天应用。
4. **`--require-identity` 默认关着**，所以默认配置下老客户端仍可无签名登录。
   要真正强制，启动时加上这个参数。
5. **配对码没有签名。** 它是一段明文配置，可以被伪造。
   没有账号体系时签名保护不了什么，但这是已知弱点。
6. **Rust 侧的握手不绑定公钥** —— `link.rs` 的 `peer_id` 是对方在 TCP hello 里
   自己填的字符串（只校验非空、不超长），不像应用层事件那样有签名。
   现在拒掉了「自称是本机 id」的那一条（否则 `node.rs` 会把它的每一帧以
   `from = 我的 id` 投上去），但**冒充一个我认识的 id 仍然可以握手成功**。
   在局域网这个威胁模型下这不算致命：进得了链路不等于进得了会话 ——
   消息要能折叠进会话，仍然得过会话层那道签名。
   要彻底解决得把 peer_id 换成公钥指纹，或让 hello 带一份自签名。

### 性能实测（Node 22，4 MB 载荷）

| 操作 | 耗时 | 吞吐 |
|---|---|---|
| AES-256-GCM 加密 | 4 ms | 1.1 GB/s |
| AES-256-GCM 解密 | 4 ms | 1.1 GB/s |
| **JS 里的 base64 编码** | **138 ms** | **28 MB/s** |
| base64 解码（`atob`） | 12 ms | 440 MB/s |

**结论有点反直觉：这条链路上真正慢的是 base64，不是加密。**
加密快三个数量级。所以「低性能占用」这一项上，瓶颈不在密码学。

试过两个「更快」的 base64 写法，都没赢：手写查表 3→4 是 151 ms（更慢），
`TextDecoder('latin1')` + `btoa` 直接抛 `InvalidCharacterError`
（WHATWG 里 latin1 是 windows-1252 的别名，0x80-0x9F 会变成 U+20AC 之类的码点）。

要真正解决得换掉 base64 本身，两个方向：

- 图片这类 data URL 先解成原始字节再加密，省掉一次 4/3 膨胀；
- 超大载荷走 WebSocket 二进制帧，不进 JSON，就完全不用 base64。

顺带一个踩过的坑：**JWK 里的 `x` 是 base64url**（`-` `_`，不带 `=`），
直接喂给 `atob` 会抛异常。而且它是**概率性**的 —— 43 个字符里恰好不出现
`-`/`_` 时能跑通，那有约 26% 的概率，也就是说大约 1/4 的密钥能过、3/4 当场炸。
第一次跑碰巧过了，第二次才暴露。所以自检里那条往返测试现在跑 40 轮。
见 `core.ts` 的 `fromB64Url()`。

## 六、怎么跑这些测试

```bash
# 密码学自检（33 项，含客户端↔服务端逐字节对拍）
npx esbuild tools/crypto-selftest.ts --bundle --format=esm --platform=node \
  --outfile=tools/.crypto-selftest.mjs && node tools/.crypto-selftest.mjs

# 身份核验端到端（18 项，自己起服务器、跑完自己杀）
node server/test/identity-e2e.mjs

# 原有回归
node server/test/smoke.mjs    ws://127.0.0.1:8787/ws
node server/test/friends.mjs  ws://127.0.0.1:8787/ws
node server/test/health.mjs
```

`identity-e2e.mjs` **刻意不复用客户端的实现**，而是用 node 自己的 crypto
重新实现一遍「客户端该做什么」。理由：如果测试复用了被测代码，
两边一起错（比如把待签文本拼错了）测试照样全绿。独立实现一遍，
才能证明「协议本身」是对的。
